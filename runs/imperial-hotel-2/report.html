What happened
The confirmation screen's 氏名 row displayed the surname as "Nguy&#7877;n" instead of "Nguyễn", while the baseline's row showed 山田 太郎 correctly. This is nanori's own measurement comparing the typed value with the review row text; the site showed no error message.
Why it matters
A person with a name of this shape, such as a Vietnamese name with diacritics, would see their name corrupted on the review screen before sending. The record the site keeps may carry the same corruption.
Basis
Page 27 item 3 asks name fields to accept Latin letters; it does not explicitly address diacritics or how a name is displayed, so the corrupted display is only inconsistent with this guidance by analogy. The guidance is for Tokyo Metropolitan Government forms and is not law. (analogy, for review; GovTech Tokyo Input Form Guidance v1.1, p.27 item 3 (accept Latin letters), by analogy)
Cause
Reproduced from the displayed text, not confirmed in source: the name appears to be double-escaped, with numeric character references such as &#7877; escaped again so they show literally. One possible trigger is a non-UTF-8 form encoding that makes the browser send characters outside the charset as references, which the server then escapes again.
Proposed repair
Serve and submit the form as UTF-8 (meta charset and accept-charset="UTF-8"), and HTML-escape the name exactly once when rendering the confirmation row. Keep the existing maxlength=64 and any server-side validation unchanged so invalid input is still rejected.
