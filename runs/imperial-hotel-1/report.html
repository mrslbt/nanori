What happened
The surname field accepted Nguyễn without error, but the confirmation screen's 氏名 row displayed it as "Nguy&#7877;n", showing literal HTML entity codes instead of ễ. The baseline's review row showed 山田 太郎 correctly, and the 'altered' label comes from nanori's checkpoint check rather than from any error message on the site.
Why it matters
A person with a name of this shape, such as a Vietnamese name with stacked diacritics, is an intended user of a registration form. They would see their name corrupted on the screen meant for checking it before sending.
Basis
Page 27 item 3 says name fields should accept Latin letters, and this form did accept the input. The guidance does not directly address how names are displayed on a review screen, so this is cited by analogy only. (analogy, for review; GovTech Tokyo Input Form Guidance v1.1, p.27 item 3 (accept Latin letters in name fields), by analogy only)
Cause
The likely cause is double escaping: non-ASCII characters appear to be converted to numeric character references and then HTML-escaped again when the review page is rendered. This is reproduced from the displayed text and not confirmed in source.
Proposed repair
Escape name values exactly once at output: store and pass the raw UTF-8 string, drop any pre-encoding to &#NNNN; references, and keep a single HTML-escape in the confirmation template. Keep the existing maxlength=64 and any other validation unchanged so genuinely invalid input is still rejected.
